## 3. 반복된 실패 패턴 (메타 원인)

세 버전 모두 같은 순서를 밟았다.

```
실패 결과 → 눈에 띄는 통계 하나 발견 → 그것을 원인으로 단정
→ 그 특성의 합성 데이터 대량 생성 → 여러 분포를 동시에 변경
→ 14시간 전면 학습 → 총점으로만 판단
```

필요했던 순서는 이것이다.

```
실패 페이지 → 단계별 분해(검출/읽기/변환/조립/위치/헤더)
→ 병목 확정 → 그 병목과 같은 데이터 소량 → V3 에서 짧은 보정
→ 예측한 실패가 실제로 통과했는지 확인
```

구체적 잘못 네 가지:

1. **한 번에 5~7개를 바꿨다.** 져도 어느 것 때문인지 못 가린다.
2. **오염된 계측으로 가설을 세웠다**(§5).
3. **값싼 사전 검증 없이 14시간에 걸었다.** V3.3 은 OOD 100% 로 "학습은 성공,
   전이는 실패" 였는데 **학습 전에 알 수 있었다.**
4. **레코드 수로 배합을 맞췄다.** 실제 gradient 는 토큰 비례다 —
   V3 표는 레코드 20.5% 인데 **토큰 52.8%** 를 먹는다(V3.3 은 55.3%).

| 표 반복 차단(cycle)을 되살리면 점수가 오른다 | 폭주 33.5→3.4% 인데 표 **−0.01p**. 토큰 −36% 비용 레버일 뿐 |

| OTSL→HTML 변환이 셀을 잃는다 | 변환 성공률 **100%**, 소실 0.5% |

## 7. V3.4 규칙

1. **한 번에 하나만 바꾼다.** 데이터 소스·비중·출발점·스케줄을 동시에 바꾸지 않는다.
2. **값싼 순서로 간다.** 추론 설정 → 후처리 → V3 기반 짧은 보정(1,000스텝) → 전면 재학습.
   전면 재학습은 앞 단계가 근거를 준 뒤에만.
3. **만들기 전에 잰다.** 목표 구조를 넣기 전에 **평가셋에서 그 구조의 출현율**과
   **가용 상한**을 먼저 측정한다. 상한이 1~2%p 면 하지 않는다.
4. **판정은 849쪽 전량 + 페이지 단위 bootstrap.** 부분집합은 후보 선별에만 쓴다.
   51쪽·269쪽 절대 점수를 61.04 와 비교하지 않는다.
5. **대표 지표를 벡터로 쓴다.** `text / table / header-footer / 문서군 4종 /
   단계별 생존 / 전이(회복·신규실패)`. 단일 macro 는 보조.
6. **합격 기준을 결과 보기 전에 고정한다.** V3.3 의 append 실험은 사전 고정한
   중복표 게이트가 잘못된 채택을 막았다.
7. **OOD val 로 "배웠나 / 전이됐나" 를 가른다.** 학습 성공과 벤치 개선은 다른 문제다.
8. **배합은 레코드가 아니라 토큰으로 맞춘다.**
9. **KDoc 은 더 이상 holdout 이 아니다.** 개발 중 반복 관찰했으므로 최종 선택용
   독립 실문서 validation 이 따로 필요하다.
10. **학습 시작은 사람이 한다.** 게이트를 통과해도 자동으로 띄우지 않는다.
11. **높은 점수를 보면 "무엇을 재는 점수인가" 부터 확인한다.** 이번에 TATR
    `projected row header` F1 90.7% 를 보고 채택할 뻔했는데, 그건 표 가로를 가르는
    **구획 제목 행**이지 KDoc 이 묻는 **왼쪽 행머리글 열**이 아니었다. V3.3 의
    "OOD 100% 인데 KDoc +1.0p" 와 같은 함정이다.
12. **없다고 단정하기 전에 보유 데이터를 뒤진다.** "행 헤더 GT 가 공개셋에 없다" 고
    했는데 이미 FinTabNet 2만건을 학습에 넣고 있었다.

## 8. 표 데이터 경로 종결 정리 (2026-08-18)

시도한 것과 결과를 한 표로 남긴다. **전부 값싼 사전검증으로 걸렀고, 학습은 하지 않았다.**

| 시도 | 비용 | 결과 |
|---|---|---|
| 합성 topology 증량 (V3.3) | 14h 학습 | OOD 100% / KDoc **+1.0p** |
| 토큰 상한 4,096→6,144 | 1h | 표 **+0.01p** (상한 도달 98.8% 유지) |
| hybrid append 조립 | 3h | 본문 +0.62p / **표 −6.56p**, 중복표 10→143 |
| cycle 재활성 5설정 | 2h | 폭주 −90% / 표 **−0.01p** |
| 전폭 crop · 밴드 분할 | 1h | 43% < 64% / 불규칙 |
| PubTables-1M 투입 검토 | 1h | 크기·병합·언어 격차 **확대** |

## 9. V3.4 표 데이터셋 플랜 — SOTA 격차 관점

V3.0 에서 문제는 "표를 아예 못 찾는다"가 아니었다. S1 Table box 생존은 99.17% 다.
SOTA 대비 약한 축은 **셀 읽기(S2 29.2% 소실)** 와 **셀 위치·관계(S4 19.6% 소실)** 다.
따라서 V3.4 데이터는 표 개수나 topology 를 더 늘리는 것이 아니라, 모델이 셀값과
행·열·병합·헤더 관계를 직접 배울 수 있는 **정답 정보 밀도**를 늘려야 한다.

### 9.1 다시 하지 않을 것

| 제외 | 이유 |
|---|---|
| cycle / 반복 차단 스윕 | 폭주는 줄였지만 표 점수 −0.01p |
| max token 4,096→6,144 | 표 +0.01p |
| append 조립 | 본문 +0.62p, 표 −6.56p |
| full-width crop / 단순 band 분할 | 재현 불규칙, 이전 검증 실패 |
| 합성 좌측계층·다단 topology 대량 증량 | V3.3 OOD 100%, KDoc 전이 +1.0p |
| 병합비율 임의 축소 | 71709 실표 병합이 가장 높음(19.5%) |
| 첫 행·첫 열 `<ched>` 휴리스틱 추가 학습 | 모델이 이미 대부분 `<th>` 를 출력, 주 병목 아님 |
| V3.1~V3.3 식 14시간 전면 재학습 | 실패 원인 분리가 안 됨 |

### 9.2 외부 데이터 — PubTables-1M 역할 재판정

| 우선 | 데이터 | 쓸 정보 | 쓰는 이유 | 합격 게이트 |
|---|---|---|---|---|
| 1 | **PubTables-1M** | column header / projected row header 정답 영역 | 학습셋도, KDoc left_heading 수도 라벨셋도 아니다. TATR 자체 검증 참고셋으로만 보존 | KDoc left_heading 과 개념 불일치 확인 완료 |
| 2 | **WTW** | wild/scanned/photo table, cell quadrilateral, row/col start/end | 실제 촬영·스캔·기울어진 표 구조 강건성. detector crop 흔들림과 S4 에 맞다 | KDoc 실패형과 비슷한 blur/skew/line-break 표가 20% 이상 |
| 3 | **FinTabNet 원천 재처리** | native cell bbox, row/col/span, text, `<th>/<thead>` 행헤더 | 좌측 행헤더 GT 는 진짜지만 V3 가 이미 FinTabNet val F1 97.7% | KDoc 전이 불가 판정. 단순 증량 금지 |
| 4 | TableBank | table bbox/grid 약지도 | detection/grid 보조. 셀값·헤더가 약하므로 후순위 | S1/S4 보조에서만 이득 있을 때 사용 |

핵심은 "외부 데이터를 많이 넣자"가 아니다. **KDoc 병목과 맞지 않는 외부 데이터를 학습에
넣으면 V3.1~V3.3 과 같은 실패를 반복한다.** PubTables-1M 은 cell graph/헤더 정답이
좋지만, KDoc 의 실제 실패 분포와 다르므로 직접 학습 투입은 보류한다.

#### PubTables-1M 직접 학습 부적합 판정

| KDoc 표 성능 병목 | PubTables-1M 실측 | 판정 |
|---|---:|---|
| 문제 표 높이 큼 | val 500 table height 중앙 204px, 1,400px 이상 0/500 | 직접 투입 시 크기 분포 격차 확대 |
| 병합/복잡 표가 실패에 강하게 연관 | PubTables spanning/complex 표 비중 낮음 | S4/S5/S6 병목 직접 타격 약함 |
| left_heading 이 약한 축 | projected row header 보유 표 94/500 = 18.8% | KDoc left_heading 78% 분포와 다름 |
| 한국어 셀값 읽기 필요 | PubTables 는 영문/깨끗한 PDF 렌더 | S2 한국어 OCR 보강 불가 |
| detector crop 흔들림·스캔 노이즈 | 정확한 PDF render/bbox | 추론 crop mismatch 해소 불가 |

따라서 PubTables-1M 의 역할은 **학습 데이터도, KDoc left_heading 수도 라벨 데이터도
아니다.** TATR 이 PubTables 자기 과제에서 헤더를 잘 잡는지 확인하는 참고 검증셋으로만
남긴다. 71709/KDoc 에는 header GT 가 없지만, PubTables 의 `table projected row header`
는 KDoc left_heading 과 개념이 다르다.

#### TATR/PubTables 수도 라벨 경로 폐기

| 항목 | 결과 |
|---|---|
| PubTables val 500 TATR 성능 | column_header F1 98.0%, projected_row_header F1 93.0% |
| projected row header 형상 확인 | 119/119 = 100% 가로 전체를 가르는 납작한 띠. 폭 비율 1.00, 높이 비율 0.04, 세로형 0% |
| KDoc left_heading | 왼쪽 세로 열/셀 계층. KDoc 테스트 출현 78% |
| 71709 한국어 표 300 대조 | 휴리스틱과 TATR 헤더 행 수 27.0% 불일치. TATR 이 맞는 예도 있지만 데이터 행까지 헤더로 잡는 과다 판정도 있음 |
| 판정 | TATR 은 자기 과제에서는 정확하지만 KDoc left_heading 을 재는 모델이 아니다. 10.4만 건 수도 라벨 주입 금지 |

#### FinTabNet 좌측 행헤더 전이 실험

| 항목 | 결과 |
|---|---:|
| FinTabNet val 표본 | 300표 |
| GT 좌측 행헤더 보유 표 | 264/300 = 88.0% |
| V3 예측 좌측 행헤더 보유 표 | 269/300 = 89.7% |
| 행 단위 Precision / Recall / F1 | 96.9% / 98.6% / **97.7%** |
| KDoc left_heading | **53.7%** |

FinTabNet 은 원천 HTML 의 `<th>/<thead>` 가 OTSL `<ched>` 로 보존되는 **진짜 GT** 다.
그러나 V3 는 이미 이 도메인의 좌측 행헤더를 거의 완벽히 맞힌다. 그러므로 FinTabNet
2만 → 6.1만 증량은 KDoc 개선 근거가 없다. 이 실험은 **물량 부족을 기각하고 도메인
격차를 확정**한다.

#### 기존 KDoc SOTA 모델을 수도 라벨러로 쓰는 조건

KDoc-OCRBench-V2 README 의 full 849 리더보드에는 우리보다 표 점수가 높은 외부 OCR
시스템이 있다.

| 모델 | KDoc Table |
|---|---:|
| BizOnAI-OCR | 58.1 |
| PaddleOCR-VL | 48.9 |
| DeepSeek OCR | 46.6 |
| olmOCR v0.2.0 | 44.9 |
| GLM OCR | 30.0 |

그러나 현재 workspace 에 확인되는 것은 우리 V3/V3.1 계열 markdown 출력과 점수 JSON 이고,
위 외부 SOTA 의 849장 markdown/HTML 출력물은 없다. 수도 라벨은 점수표에서 만들 수 없고,
각 페이지의 실제 표 출력이 있어야 한다.

따라서 가능한 경로는 **조건부 가능**이다.

| 단계 | 판정 |
|---|---|
| 1. SOTA 출력 확보 | 필요. `olmOCR` bench convert 가 지원하는 `chatgpt/gemini/mistral/marker/mineru/olmocr_pipeline` 또는 별도 PaddleOCR-VL/BizOnAI/DeepSeek 실행 결과가 필요 |
| 2. KDoc 849 또는 최소 200~300표에서 축별 자격시험 | 필수. 전체 table 점수가 아니라 `cell`, `top_heading`, `left_heading`, `span/position` 별로 분해 |
| 3. left_heading teacher F1 기준 | 사람 검수 또는 KDoc verified unit 기준으로 90% 이상이면 채택, 80~90%면 보조/합의 라벨, 80% 미만이면 폐기 |
| 4. 라벨 채택 방식 | 단일 SOTA 전체 출력 금지. 2개 이상 teacher 합의 또는 SOTA+V3 일치 셀만 채택 |
| 5. 불일치 처리 | cell text/구조/헤더가 어긋나는 셀은 loss mask. 억지 GT 금지 |

즉 “기존 SOTA 모델로 수도 라벨을 할 수 있나?”의 답은 **예, 하지만 현재 보유 상태로는
바로는 불가**다. 필요한 것은 모델 이름이나 리더보드 점수가 아니라, KDoc/71709 페이지별
출력과 left_heading 축 자격시험이다.

#### BizOnAI-OCR teacher 자격시험 1차 (2026-08-18)

KDoc 리더보드에서 표 점수가 가장 높은 BizOnAI-OCR 을 먼저 실제 실행했다. Hugging Face
모델 `ONTHEIT/BizOnAI-OCR` 을 로컬에 받고(`.hf_bizonai`, 약 17GB), vLLM 0.11.0 서버를
GPU 1장에 올렸다. Transformers 직접 실행은 페이지당 수분으로 느려서 5쪽 이상 자격시험에
부적합했고, vLLM 서버는 약 25~33초/쪽으로 동작했다.

실행 산출물:

- 서버용 생성기: `tools/run_bizonai_kdoc_teacher_vllm.py`
- 축별 채점기: `tools/eval_kdoc_teacher_axes.py`
- 출력: `results/teacher_bizonai/kdoc_short5_vllm`
- 채점 JSON: `results/teacher_bizonai/axes_short5_vllm.json`
- 비교 V3 출력: `results/teacher_bizonai/v3_tuned_short5`
- 비교 JSON: `results/teacher_bizonai/axes_v3_tuned_short5.json`

### 9.3 의사생성 데이터 — 실제 한국 문서에서 자동 정답을 만든다

| 단계 | 할 일 | 실패 방지 게이트 |
|---|---|---|
| 1 | 한국 공공 PDF 중 디지털 PDF 를 모아 텍스트 좌표·선분·표 영역을 추출한다 | PDF 텍스트와 렌더 이미지 OCR 일치율 ≥98% |
| 2 | vector line/grid 로 row/col/cell 후보를 만든다 | 100표 수동 검수에서 셀 bbox IoU 통과 ≥95% |
| 3 | teacher 3개를 합의시킨다: PDF vector parser + PubTables/TATR 계열 구조모델 + V3 OCR | 불일치 cell 은 loss mask, 억지 GT 금지 |
| 4 | 정확한 PDF crop 과 V3 detector crop 을 둘 다 저장한다 | detector crop 에서 보이는 cell 만 target 으로 남김 |
| 5 | 같은 셀 그래프에서 relation 질문을 자동 생성한다 | top/left/row/col/span 별 정답 커버리지 리포트 필수 |
| 6 | blur/compression/skew/line removal/crop jitter 를 렌더링한다 | 원본 graph 보존 검증 100% |

이건 이전의 "합성 topology 만들기"와 다르다. 표 모양을 상상해서 만드는 게 아니라,
**실제 문서의 표 구조를 자동 라벨링**하고, 확신 없는 칸은 학습에서 빼는 방식이다.

### 9.4 현재 데이터 수정 — OTSL 단일 정답에서 셀 그래프로 승격

| 수정 | 목적 |
|---|---|
| 모든 표 소스를 `cell_graph` 스키마로 통일 | bbox, row, col, rowspan, colspan, text, role, provenance, confidence 보존 |
| OTSL/HTML 은 `cell_graph` 에서 파생 | 문자열 규약이 원천 정답을 덮어쓰지 못하게 함 |
| header 확신 없는 셀은 header loss mask | 휴리스틱 GT 로 모델을 흔들지 않음 |
| 긴 표는 레코드가 아니라 토큰·셀 수로 loss 정규화 | 긴 합성표가 gradient 를 독식하지 않게 함 |
| V3 가 이미 맞힌 표를 frozen replay 로 유지 | 표를 올리면서 기존 정답을 깨는 회귀 방지 |
| 실패 유형별 bucket 구성 | cell_read / position / top / left / long / merged / empty 를 따로 추적 |

### 9.5 학습 방식

1. V3 에서 시작한다. V3.4 는 `stage1b` 재출발 금지.
2. 처음은 표 전용 adapter/head 만 짧게 학습한다.
3. loss 는 `cell text`, `row/col`, `span`, `header role`, `top/left relation`, `serialization` 으로 분리한다.
4. 표 OTSL 생성만 보지 말고 relation probe 를 매 eval 마다 본다.
5. 1,000스텝 안에 S2 또는 S4 가 오르지 않으면 중단한다.
6. 849쪽 전량에서 table +1.0p 이상, text −0.3p 이내, duplicate table 증가 없음일 때만 다음 단계로 간다.

### 9.6 우선순위

| 순서 | 작업 | 기대 이득 | 중단 조건 |
|---|---|---|---|
| 0 | 배치 의존 붕괴 재현·수정 | 데이터 이전의 신뢰도 회복 | batch=1/8 결과가 다르면 학습 금지 |
| 1 | `cell_graph` 스키마와 evaluator 작성 | 모든 데이터의 공통 기준 | 71709/PubTabNet/FinTabNet 100건 왕복 실패 >2% |
| 2 | **oracle crop vs detector crop mismatch 검증** | S2 셀 읽기·S4 위치의 입력 차이 확인 | oracle crop 이 detector crop 대비 S2/S4 를 못 올리면 crop 증강 경로 중단 |
| 3 | 격자 붕괴 배치 의존 재현·고정 | 같은 입력이 배치에 따라 달라지는 불안정 제거 | batch=1/8/동일배치 결과 불일치가 남으면 학습 금지 |
| 4 | 기존 KDoc SOTA 출력 확보 후 teacher 자격시험 | KDoc식 표/left_heading 수도 라벨 가능성 확인 | left_heading F1 90% 미만 또는 SOTA 간 불일치 과다 시 단독 라벨 금지 |
| 5 | 한국 디지털 PDF 의사라벨 1,000표 | S2 한국어 셀값 + S4 실제 레이아웃 | 100표 검수 정확도 <95% 면 중단 |
| 6 | real-graph 기반 렌더 증강 | detector crop 흔들림 적응 | oracle crop 대비 detector crop 격차가 안 줄면 중단 |
| 7 | V3 표 전용 1,000스텝 보정 | 실제 성능 확인 | table +1p 미만 또는 text 회귀면 폐기 |

**정리.** V3.4 의 표 성능업은 "표 데이터를 더 많이"가 아니라
**정답 정보가 더 많은 표 데이터**가 필요하다. V3.1~V3.3 은 OTSL 문자열과 합성 구조를
늘렸고, SOTA 대비 부족한 cell graph/position/relation 감독은 거의 늘리지 못했다.


## 10. 다음에 검증할 것 (우선순위)

### ★ 2026-08-18 추가로 확정된 것 — 구조 지식은 이미 있다

같은 결론이 **두 번 독립적으로** 나왔다.

| 실험 | 학습·유사 도메인 | KDoc |
|---|---|---|
| V3.3 OOD val (합성 계층표, unseen 어휘) | **100%** | left_heading **+1.0p** |
| **V3 × FinTabNet 좌측 행헤더 (진짜 `<th>` GT)** | **F1 97.7%** | left_heading **53.7%** |

모델은 "좌측 행헤더" 개념을 **완전히 배웠는데** 한국어 스캔 공공문서에서 못 쓴다.
따라서 **"표 구조 데이터를 더/잘 넣는다" 는 경로는 닫혔다.** 남은 차이는 구조 지식이
아니라 **입력**(한국어·스캔·detector crop)이다 — 즉 S2 읽기 29.2% · S4 배치 19.6%.

### ★ crop 불일치 — 오늘 유일하게 **효과가 측정된** 항목 (2026-08-18)

71709 실표 200건에 같은 표를 두 조건으로 넣었다(V3, `tools/eval_crop_robustness.py`).

| | 셀 recall 평균 | 중앙 |
|---|---|---|
| A 정답 crop (학습과 같은 형태) | **88.5%** | 92.5% |
| B 교란 crop (한 변 2~8% 잘림 + 반대편 3~10% 확장) | **84.2%** | 88.2% |
| 차이 | **−4.3p** | — |

200건 중 **63건(31.5%)** 이 5p 이상 악화했다. **반증되지 않은 첫 항목**이다.

다만 **격차의 일부만 설명한다.**

| | |
|---|---|
| 깨끗한 crop 에서 V3 셀 recall | 88.5% |
| KDoc S2 생존 | 69.84% |
| 격차 | 약 **19p** |
| crop 교란이 설명하는 몫 | **4.3p (약 23%)** |

★ 이 실험이 보인 것은 **"V3 가 교란에 약하다"** 이지 **"증강하면 고쳐진다"** 가 아니다.
  증강 학습이 강건성을 올리리라는 것은 아직 **추론**이다 — 규칙 3번(만들기 전에 잰다)에
  따라, 증강 데이터를 만들기 전에 소규모 보정으로 효과를 먼저 확인한다.

| # | 가설 | 검증 비용 | 상태 |
|---|---|---|---|
| 1 | crop 증강 학습이 실제로 강건성을 올리는가 | V3 짧은 보정 1,000스텝 ≈ 2h | **다음 차례** |
| 2 | 격자 붕괴가 배치 구성에 의존하는가(배치 1 / 8 / 동일배치 2회) | 1시간 | 진행 중 |
| 3 | 레이아웃 토큰 비중 7.8%(V3 15.0%)가 머리말·분류에 영향을 주는가 | 중간 | 미검증 |
| 4 | 독립 실문서 holdout 구축 | 며칠 | 미착수 |

1번이 통과하면 **주석 없이** 증강으로 데이터를 만들 수 있고, S2(29.2%)·S4(19.6%)를
겨냥하는 첫 시도가 된다. 실패하면 **기존 crop 증강으로는** S2·S4 를 고치기 어렵다는
뜻이다. 그때는 V3 를 임시 기준선으로 고정하고, 아래 §9 의 "정답 정보가 더 많은 표 데이터"로
재설계한다.

**2026-08-18 추가 판정.** 표 구조/헤더 데이터 경로는 대부분 닫혔다. V3.3 은 합성 계층표
OOD val 을 100% 복원했지만 KDoc 은 +1.0p 에 그쳤고, V3 는 FinTabNet 좌측 행헤더를
F1 97.7% 로 맞히지만 KDoc left_heading 은 53.7% 다. 즉 모델이 좌측 행헤더 개념을
모르는 것이 아니라, **영문 금융/합성 표 구조 지식이 한국어 스캔 공공문서 입력으로
전이되지 않는다.** 남은 핵심은 구조 개념 증량이 아니라 입력 차이, 특히 S2 raw OTSL
셀 읽기와 S4 위치 배치다.

#### ★ §9.5 계획과 실제 실행의 차이 (기록)

| 표만 상승, 본문·머리말 하락 | 폐기 또는 **낮은 step 체크포인트** 선택 |
| 표 안 오름 | **OTSL 통짜 경로 폐기** → cell_graph / partial-mask 로 |
| **S2·S4 안 오르고 top/left 만 출렁** | **목표 병목 못 때림 = 실패** |

★ 마지막 줄이 핵심이다. 표 점수가 우연히 올라도 **S2·S4 가 안 움직였으면 실패**로 본다.
  `final` 만 보지 않고 500·1000·1500 을 함께 평가해 **투여량-반응 곡선**으로 판단한다.

#### ★ OCR 관점 보조 평가 추가 — heading 형식과 문자 생존 분리 (2026-08-20)

기존 KDoc table 점수는 OCR 문자 인식과 표 의미 구조를 한 번에 묶는다. 특히
`left_heading` 은 `<th>` 역할·heading path 까지 맞아야 통과하므로, **문자는 읽었는데
형식/역할 때문에 실패한 경우**가 숨는다.

따라서 공식 점수는 유지하되, 내부 진단용으로 `tools/eval_kdoc_ocr_text_axes.py` 를 추가했다.

| 지표 | 의미 |
|---|---|
| `cell_text` | 타깃 셀 문자를 읽었는가 |
| `cell_text_compact` | 모든 공백을 제거한 뒤 타깃 셀 문자가 맞는가 |
| `position_text` | 타깃 셀 주변 up/down/left/right 문자를 맞혔는가 |
| `left_heading_text_anywhere` | 정답 left heading 문자열이 예측 표 어딘가에 살아있는가 (`<th>` 무시) |
| `left_heading_row_aware` | 정답 left heading 문자열이 타깃 셀의 왼쪽/같은 행 문맥에 있는가 (`<th>` 무시) |
| `table_text_all_anywhere` | KDoc 테스트가 요구하는 cell/up/down/left/right/top/left-heading 문자열이 같은 예측 표 안에 모두 있는가. 행열·`<th>`·GT path 무시 |
| `table_text_all_anywhere_compact` | 위와 같되 모든 공백을 제거하고 비교한다 |
| `role_agnostic_all` | cell+position+top/left heading 텍스트는 맞지만 heading role 은 무시한 통과 |
| `strict_all` | 기존 strict table 통과 |

V3 기준(`results/kdoc_md/v3_tuned_full`, 49,115 tests):

|---|---:|
| `cell_text` | **67.97%** |
| `position_text` | **49.04%** |
| `left_heading_text_anywhere` | **50.05%** |
| `left_heading_row_aware` | **41.09%** |
| `table_text_all_anywhere` | **37.82%** |
| `role_agnostic_all` | **34.67%** |
| `strict_all` | **26.65%** |

`left_heading` 이 필요한 subset(38,520 tests):

| 지표 | needs_left |
|---|---:|
| `cell_text` | **68.70%** |
| `position_text` | **51.03%** |
| `left_heading_text_anywhere` | **63.81%** |

해석: V3 는 needs_left 에서 left heading 문자열 자체를 **63.81%** 살리지만, 같은 행/왼쪽
문맥으로 가면 **40.88%**, strict 구조 통과는 **24.82%** 로 떨어진다. 즉 left_heading
실패의 상당 부분은 "문자를 못 읽음"만이 아니라 **행/열 배치와 heading role 형식 문제**다.

앞으로 V3.4t 판정은 공식 `tables` 점수와 별도로 이 OCR 보조축을 같이 본다. OCR 제품 관점에서는
`cell_text`, `left_heading_text_anywhere`, `left_heading_row_aware` 가 오르는지 먼저 확인한다.
공식 채택 기준은 그대로 두되, strict 점수가 정체되어도 OCR 문자 생존율이 오르면 다음 실험은
`cell_graph / partial-mask / role 후처리` 로 분기한다.

1. 외부 SOTA 는 공식 strict table 리더보드 비교용이다. 내부 `cell_text` 류 분해 출력이 없으므로 OCR 정보 생존 칸은 비운다.
2. 우리 모델은 공식 strict 와 내부 OCR 정보 생존을 둘 다 본다.
3. V3.4t final 은 리더보드식 최종 모델로는 미채택이지만, **표 OCR 문자/정보 생존을 실제로 올린 첫 성공 사례**다.

단, 이 `final` 을 그대로 배포하지 않는다. 본문 손상을 막기 위해 다음 판정 순서는:

1. 250/500/750/1000/1250/1500 체크포인트에서 같은 OCR 수정 평가를 돌린다.
2. `cell_text` 상승이 유지되면서 본문 회귀가 가장 작은 step 을 고른다.
3. 다음 학습은 전체 파라미터가 아니라 **표 adapter/head 또는 partial-mask** 로 제한한다.
4. strict 구조 점수는 참고 지표로 두고, 표 OCR 주지표는 `cell_text_compact`,
   `table_text_all_anywhere_compact`, `left_heading_text_anywhere`, `left_heading_row_aware` 로 본다.

### 11.7 ★ V3.4t 체크포인트 스윕 — **s1500 이 최적** (2026-08-20 밤)

학습이 step 1,620 에서 완주했다(eval loss 500 → 0.1122, 1000 → 0.1089, 1500 → **0.1080** 단조 하락).
§11.6 말미의 판정 순서 1번대로 체크포인트별로 849쪽 전량을 다시 쟀다.

평가 스크립트: [scripts/eval_v3_4t_ckpts.sh](../../scripts/eval_v3_4t_ckpts.sh) ·
공백무시 채점기: [tools/eval_kdoc_compact_score.py](../../tools/eval_kdoc_compact_score.py) ·
축 분해: [tools/eval_kdoc_ocr_text_axes.py](../../tools/eval_kdoc_ocr_text_axes.py)

#### (0) 평가 방법 — 재현 절차

**모든 체크포인트가 완전히 같은 조건으로 추론·채점됐다.** 비교 가능성의 전제이므로 전부 남긴다.

**입력** — `<PAGES_DIR>/*.jpg` **849장**(KDoc-OCRBench-V2 전량). 표본 아님.
GT 는 `<DATA_ROOT>/BENCHMARK/KDoc-OCRBench-V2` 의
`text_present.jsonl`(6,290) · `tables.jsonl`(49,115) · `header_footer_tests.jsonl`(792) = **56,197 테스트**.

**추론** — [benchmark/run_pages.py](../../benchmark/run_pages.py), GPU 8장에 `--shard i --num-shards 8` 로 쪼갬.
체크포인트 경로만 바뀌고 나머지 인자는 **전부 동일**하다:

```
CUDA_VISIBLE_DEVICES=$i python benchmark/run_pages.py \
  --model outputs/pierrotocrvlm_v3_4t/checkpoint-1500 \
  --images "<PAGES_DIR>/*.jpg" --out results/kdoc_md/v34t_s1500 \
  --mode hybrid-page --hybrid-place replace --table-pad 0.02 --table-stop-on-cycle 0 \
  --shard $i --num-shards 8
```

`--mode hybrid-page --hybrid-place replace` 는 V3 기준선을 만들 때와 같은 조립 모드다
(§4.5 의 F안은 **아직 안 들어갔다** — 이번 비교에는 미적용).
`--table-stop-on-cycle 0` 으로 반복 억제도 껐다. 즉 **이번 차이는 순수하게 가중치 차이**다.

**기준선** — `results/kdoc_md/v3_trace/` (V3 의 849쪽 출력). 이 출력의 공백무시 점수는
기존 `results/full849_v3_tuned_full_compact.json` 과 `62.93 / 42.42 / 96.97` 로 **완전히 일치**한다.
즉 기준선을 새로 추론하지 않고 기존 산출물을 그대로 썼다.

**채점 — 3축(주 보고 기준)**: [tools/eval_kdoc_compact_score.py](../../tools/eval_kdoc_compact_score.py).
공식 KDoc scorer 를 그대로 쓰되 **문자열 비교 직전에 공백만 제거**한다. presence 판정,
표의 cell/up/down/left/right, top/left heading path, 3축 평균 계산은 **공식과 동일**하다.

```
python tools/eval_kdoc_compact_score.py --pred results/kdoc_md/v34t_s1500 --out results/ns_v34t_s1500.json
```

**채점 — OCR 축 분해(보조)**: [tools/eval_kdoc_ocr_text_axes.py](../../tools/eval_kdoc_ocr_text_axes.py) **`--full`**.

```
python tools/eval_kdoc_ocr_text_axes.py --pred results/kdoc_md/v34t_s1500 --full --out results/axes_v34t_s1500.json
```

★ `--full` 이 중요하다. 이 도구는 기본이 `--sample-only` 라서 빠진 예측을 실패로 안 센다.
`--full` 로 돌린 결과는 `sample_only: false`, `missing_pages: 0`, 표 테스트 채점 페이지 **760쪽**
(나머지 89쪽은 표 테스트가 없는 쪽), 표 테스트 **49,115건 전량**이다.

**산출물** — 이 절의 모든 수치는 아래 파일에서 나왔다. 재계산 가능:

| 체크포인트 | 예측 markdown | 공백무시 3축 | OCR 축 분해 |
|---|---|---|---|
| V3 (기준선) | `results/kdoc_md/v3_trace/` | `results/ns_v3_trace.json` | `results/axes_v3_trace.json` |
| s1000 | `results/kdoc_md/v34t_s1000/` | `results/ns_v34t_s1000.json` | `results/axes_v34t_s1000.json` |

**아직 안 한 것** — 페이지 단위 부트스트랩 CI. 따라서 이 절의 `+3.23p` 는 **점추정이고
유의성은 미확정**이다. 테스트가 페이지 단위로 뭉쳐 있어 테스트 단위 CI 는 쓰면 안 된다(규칙 6번).

#### (1) 계측 오류 10건째 — 채점기를 섞어 비교했다

`full849_v34t_final_compact.json`(공백무시) 을 `full849_v3_tuned_full.json`(strict) 과 나란히 놓고
"표 +18.03p" 라고 읽은 적이 있다. **틀렸다.** `compact` 는 모델 변형이 아니라 **공백을 제거하고
비교하는 채점기**다. 규칙 4번(같은 하네스로만 비교)을 스스로 어긴 사례라 여기 남긴다.

| 결함 | 잘못 나온 값 → 실제 |
|---|---|
| strict 기준선 vs compact 후보를 한 표에 비교 | 표 "+18.03p" → **+2.26p**(같은 compact 기준) |

#### (2) 3축 성적 — 채점기에 따라 결론이 **뒤집힌다**

| 채점 | 모델 | 본문 | 표 | 머리말 | macro |

### 11.8 본문(Long Text) 실패 분해 — **절반이 "아예 없음"** (2026-08-20 밤)

표만 분해하고 본문은 한 번도 분해하지 않았다는 지적에 따라, V3 의 849쪽 trace
(`results/kdoc_md/v3_trace/*.layout.json`, `page_md` 와 crop 원시 출력 `trace[].raw` 보유)로
`text_present` 실패 2,332건을 원인별로 나눴다. 공백무시 기준.

판정 순서: ① `page_md` 에는 있는가 → ② crop 원시 출력/레이아웃 텍스트에는 있는가 →
③ 질의의 앞·뒤 절반 중 하나라도 있는가 → ④ 아무 데도 없는가.

| 원인 | 건수 | 실패 중 비중 |
|---|---:|---:|
| ① 조립에서 잃음 (`page_md` 엔 있음) | 174 | 7.5% |
| ② crop 인식엔 있음 (조립 누락) | 627 | 26.9% |
| ③ 부분만 읽음 (OCR 오류) | 355 | 15.2% |
| **④ 아예 없음 (미인식·영역 누락)** | **1,176** | **50.4%** |
| 합계 | 2,332 | 100% |

읽는 법:

- **①+② = 801건(34.4%) 은 이미 읽었는데 최종 markdown 에 못 담은 것**이다. 모델을 더
  학습시킬 필요 없이 **조립 로직만 고치면 회수 가능**한 분량이다. 이 중 ① 174건은 V3.4t 에서
  이미 **0건**이 됐다(→ 메모리 `pierrot-vlm-longtext-assembly` 의 hybrid 수정 효과).
- **④ 1,176건(50.4%) 이 진짜 병목**이다. crop 에도 `page_md` 에도 흔적이 없다.
  레이아웃이 영역을 아예 안 잡았거나, 잡고도 생성이 비었거나, 페이지 통읽기가 건너뛴 경우다.
  **아직 이 셋 중 무엇인지 가르지 않았다** — 다음 계측 대상.
- ③ 355건(15.2%) 은 순수 인식 품질 문제. 티처 증류가 듣는 영역이다.

실패가 몰린 문서 예: `(대량) 경상북도_포항시_열린포항소식지 13` — 소식지형 다단 편집,
`전시해설 : 6/8부터 평일 11시, 15시 / 주말 11시, 14시, 16시` 같은 줄이 crop 에는 있는데
조립에서 빠졌다(②). 잡지형 레이아웃이 취약하다.

★ 다음 계측: ④ 1,176건에 대해 (a) 해당 GT 문자열의 bbox 가 레이아웃 박스에 덮이는가,
(b) 덮인다면 그 crop 의 생성 결과가 비었는가 — 이 둘로 갈라야 처방이 정해진다.

## 12. 후속 — 원인이 조립에 있었다 (2026-08-20, V3.5)

이 문서는 V3.1~V3.3 이 **데이터로** 진 이유를 정리했다. 그런데 그 뒤 849쪽을 다시
분해하니 본문 실패의 **34.4% 가 데이터가 아니라 조립**이었다.

`--mode hybrid-page` 의 `merge_page_base` 가 page 통읽기를 골격으로 두고 **표 crop 만
이식**한다. `Text` `List-item` `Section-header` `Caption` `Footnote` `Title` crop 은
한 글자도 쓰이지 않는다. page 통읽기가 무너진 쪽에서는 잘 읽어 둔 crop 까지 함께 버려진다.

`body_fill`(못 덮은 본문 crop 만 첨부, HF crop 제외)로 **학습 0**:

| 채점 | Long Text | 3축 |
|---|---:|---:|
| 공백무시 | 62.93 → **74.74 (+11.81p)** | 67.44 → **71.29 (+3.85p)** |
| 정식 | 58.86 → **70.45 (+11.59p)** | 61.04 → **64.86 (+3.82p)** |

849쪽 재추론 검증 완료. 표 점수는 불변(42.42/26.65).

★ **이 문서에 추가할 교훈** — §5(측정 오류)에 13번째로 넣는다.

> **파이프라인을 고정 상수로 두고 데이터만 의심했다.** V3.1~V3.3 세 번 모두 조립은
