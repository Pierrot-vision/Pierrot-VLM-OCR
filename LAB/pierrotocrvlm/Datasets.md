### 1.8 한국 공공문서 **페이지 silver** — 3,461 → **44,120** (2026-08-13 확대)

우리에게 한국어 **페이지 단위** 정답이 사실상 없었다(wiki_ko 렌더 199K·synth_ko 59K 는
둘 다 합성). v3 에서 긴 텍스트가 60.3 → 56.1 로 밀린 것도 이 공백과 맞물린다.
**줄 GT(진짜) + 의사 레이아웃(그룹·순서 보조)** 으로 페이지 Markdown 을 합성한다 —
[build_ko_page_silver.py](../../tools/build_ko_page_silver.py).

★ 규약 — ① **텍스트 정답은 줄 GT 만.** teacher 인식 문자로 덮으면 교사 오류가 정답이 된다.
의사 레이아웃은 묶음·읽기순서·계층(`#`/`##`/`-`)에만 쓴다. ② **표가 있는 페이지는 버린다.**
자리표시자를 넣으면 "표를 생략하는 습관"을 배운다. ③ 출력 규약은
`to_markdown()`(infer) 과 **글자 단위로 일치**시킨다(캡션 `*…*` 포함).

**8/12 판(3,461건)의 상한은 의사 레이아웃 62,364쪽이었다.** 그래서 8/13 에

#### ⚠ 이 데이터가 **못 하는 것** 두 가지 (실측)

**① 긴 텍스트를 못 고친다.** 중앙 230자 · p90 355자 · **최대 758자**다. 71299/71300 은
1990년대 스캔 공문·서식이라 3,000쪽 표본에 **31줄 이상 페이지가 0장**이다
(6~15줄 2,368장 · 16~30줄 624장). KDoc 긴 텍스트는 현대 소식지·보고서라 밀도가 다르다.
→ 긴 페이지는 **합성(§1.9 계열)으로 직접 만들어야 한다.**

**② 문장부호를 지우도록 가르친다.** AI-Hub 라벨이 `·`·`○`·`※` 를 뺀다.
원본 `○ 청소년유해매체물의 판매·대여·배포·시청` → GT `청소년유해매체물의 판매 대여 배포 시청`.
천자당 빈도 대조:

| | `·` | `○` | `※` | `,` | `:` |
|---|---|---|---|---|---|
| **KDoc 정답** | **3.07** | **1.13** | **1.08** | 13.37 | 4.69 |
| ko_page_silver | 0.28 | 0.17 | 0.02 | 6.18 | 1.00 |
| wiki_ko | 0.52 | 0.01 | 0.00 | 8.34 | 2.99 |

KDoc 긴 텍스트 판정은 `max_diffs: 1` 이라 가운뎃점 몇 개만 빠져도 그 테스트는 실패한다.
→ **배합 비중을 낮게 잡고**(페이지 프롬프트 전체의 10% 이내), 부호가 정확한 합성 페이지와
반드시 섞는다. 물량을 근거로 비중을 올리면 안 된다.

### 3.3 압축을 풀지 않는다

`/data1` 은 Lustre 라 작은 파일 **생성**이 138장/분이다(실측). 로컬 ext4 는 43,000장/분.
88(28만 장)을 푸는 데만 34시간이 걸린다.

→ 로더가 `"<zip 경로>!<내부 경로>"` 를 직접 읽는다([jsonl.py](../../pierrot/data/jsonl.py)의
`open_image` / `_open_in_zip`). **실측 성능 차이 1.4%**(zip 29.3ms/장 vs 파일 28.9ms/장).
88·71730·LLaVA-Pretrain 이 이 방식이다. 71709 표 이미지만 예외로 로컬 ext4 캐시
(`<CACHE_DIR>/aihub/71709`)에 둔다 — 원천 zip 이 부분만 받아져 있어 재구성이 필요했다.

**tar.gz 는 안 된다.** 로더는 zip 과 **비압축** tar 만 연다. gzip 은 스트림이라 멤버
하나를 읽을 때마다 처음부터 다시 풀어야 해서 O(n²)다. PubTables-1M 이 30GB tar.gz 로
와서 ocr_9 22.4만 건이 **전부 열기 실패**했는데, 로더가 못 여는 이미지를 이웃 샘플로
조용히 대체하는 탓에 에러 하나 없이 Stage 1A/1B 각 6만·Stage 2/3 replay 4만 슬롯이
날아가고 있었다. [repack_pubtables_zip.py](../../tools/repack_pubtables_zip.py) 가 tar.gz 를
한 번만 순차로 훑어 필요한 멤버만 무압축 zip 으로 옮기고 JSONL 경로를 바꾼다.
→ **새 데이터가 tar.gz 로 오면 먼저 zip 으로 재포장하라.**

### 3.3.1 PDF 렌더는 JPEG 로 (olmOCR)

olmOCR 은 유일하게 렌더가 필요한 데이터다(PDF→이미지). 처음 PNG 로 뽑았다가 장당
1.1MB 가 나와 로컬 디스크 63GB 를 다 채웠고, `/tmp` 가 같은 파티션이라
multiprocessing 이 임시파일을 못 써서 **학습 프로세스가 죽었다**. JPEG q88·DPI 130 은
장당 ~150KB 로 7배 작고 OCR 타깃 품질에는 영향이 없다. 빌더에 여유 12GB 미만이면
멈추는 가드를 넣었다([build_olmocr_jsonl.py](../../tools/build_olmocr_jsonl.py)).

또 하나 — olmOCR 의 PDF 는 **페이지 단위로 잘려** 저장돼 있다(`<해시>-4.pdf` = 원본
4쪽). parquet 의 `page_number` 는 원본 기준이라 그대로 색인하면 1쪽짜리 문서에서 범위를
벗어나 전부 버려진다. 실제로 12만 요청에 2.7만만 살아남았다.

### 3.5 신규 3종을 빌드할 때 (2026-08-12)

§1.6 의 세 데이터셋은 각자 다른 함정이 있다. 빌더를 쓰기 전에 읽을 것.

**71553 — 좌표가 퍼센트다.** 라벨은 메뉴 항목 단위이고 박스가
`ocr:{x, y, width, height, rotation, text}` 인데 **0~100 비율**이다. 픽셀은
`meta.image_original_width/height`(3000×4000)로 환산하고, `rotation`(도)이 따로 있으니
회전 박스를 축정렬로 바꿀지 정해야 한다. 이미지 파일명에만 `-tf` 접미사가 붙어 라벨과 stem 이
다르다(`..._5-tf.jpg` ↔ `..._5.json`) — 짝을 맞출 때 접미사를 떼야 한다. **실제로 이걸
빠뜨려 9만 장 전부 "이미지 결측"으로 버려졌다**(빌드 결과 0건). 접미사를 떼자 crop
199,500 / 검출 89,500 이 나왔다. 항목마다
`ko/en/ja/zh_CN/zh_TW` 번역과 가격·재료·알레르기가 들어 있어 인식 밖 태스크도 만들 수 있다.

**105 — Validation 라벨이 두 곳에 있다.** 원천 zip 이 jpg 와 json 을 함께 담는데 라벨 zip 이
같은 json 을 또 담는다. `2.Validation/02.돌출간판/`(jpg+json)과
`2.Validation/1.간판/2.돌출간판/`(json 만) 7,130건이 겹쳐서, 파일을 그냥 세면 json 이
540,607개지만 고유 stem 은 533,477개다 — **stem 기준으로 dedup** 할 것. 그리고
`1.Training/1.간판/3.세로형간판` 에 이미지 없는 라벨 8건이 있다(AI-Hub 원본 결측, 해제 실패
아님) — 이미지 존재를 확인하고 건너뛴다. 라벨 없는 이미지는 0건이다.

**71845 — 원천이 이미지가 아니다.** 논문 PDF·PPTX 각 9,000편이고, 라벨은 단락별
`original_text` + `location`(**EMU** 단위, 914400/inch) + `summary_text` 다. 페이지 이미지를
얻으려면 PDF 를 렌더해야 하며 §3.3.1 과 같은 이유로 **JPEG q88·DPI 130** 을 쓴다(PNG 는 장당
1.1MB 라 로컬 디스크가 찬다). 단락 박스는 EMU→픽셀 환산이 필요하다. 디지털 태생 PDF 라 GT 는
정확하다. `summary_text` 는 요약이라 우리 태스크에 없으니 버린다.

### 3.6 71845 학술논문을 이번 재학습에서 제외한 이유 (2026-08-12)

**데이터를 폐기한 것이 아니다.** 현재 Stage 2 재학습의 목적(KDoc 표·fine layout)에
비해 품질 위험이 커서 보류한 것이다.

1. **띄어쓰기 결함이 표본 문단의 59%** (17개 중 10개). 실측 예:
   `자신이 살았던20세기를`, `인간사에서수행하는거대한역할에 비해폭력그자체에`.
   우리 한국어 페이지 NED 는 이미 **0.0178** 로 강한 구간이라, 이 정답으로 학습하면
   기대이익보다 퇴행 위험이 크다.
2. **페이지 매핑이 불안정하다.** 표본은 17개 문단이 전부 `page=1` 이다. 어느 문단이
   어느 페이지 이미지에 속하는지 못 믿으면 페이지 통읽기 GT 를 만들 수 없다.
3. **좌표가 EMU** 라 레이아웃·crop 을 만들려면 PPTX 슬라이드 크기 환산이 선행돼야 한다.
4. KDoc 의 주 병목은 페이지 OCR 이 아니라 **표 구조와 fine-layout 누락**이다(§3.7·
   [성능업데이트.md](성능업데이트.md)). 지금 이 비용을 쓸 자리가 아니다.

⚠ **"띄어쓰기 정상 문단만 골라 쓰기"도 하지 않는다.** 정상 여부를 자동 판정하면
짧은 문장·영문·수식 위주로 **선택 편향**이 생기고, 페이지 매핑 문제는 그대로 남는다.
crop 단위 OCR 데이터가 더 필요해질 때 별도 정제 실험으로 다룬다.

### 3.6.1 한국어 fine layout 의사 라벨 (2026-08-12)

fine 레이아웃 gold 는 ccpdf(영문)·DocLayNet(영문)·DocSynth(합성 영문)뿐이고 한국어는
synth_ko 합성이 전부였다. 그래서 한국 공공문서에서 c2f 1단계가 무너진다 — **KDoc 파국
페이지의 절반이 "Table 미검출"** 이다.

AI-Hub 문서 계열은 **페이지 이미지와 줄 박스는 진짜 GT** 인데 클래스가 없다. 그래서
박스를 새로 찍는 게 아니라 **클래스만 외부 모델로 붙이는** 문제로 좁혔다.
라벨러는 **DocLayout-YOLO (DocStructBench)** —
[build_korean_layout_pseudo.py](../../tools/build_korean_layout_pseudo.py).

★ 그대로 쓰면 안 된다. DocLayout-YOLO 에는 우리 fine 규약의 두 클래스가 없다.

| 클래스 | 보정 전 | 보정 후 | 영문 gold(ccpdf) |
|---|---|---|---|
| Title | 49,680 (20%) | **23,265 (8.0%)** | 1.7% |
| Section-header | **0** | **26,415 (9.1%)** | 13.1% |
| List-item | **0** | **4,644 (1.6%)** | 13.3% |
| Table | 39,647 (13.6%) | 39,647 (13.6%) | 2.1% |

[fix_pseudo_layout_classes.py](../../tools/fix_pseudo_layout_classes.py) 가 두 가지를 고친다.
① 한 쪽에 Title 이 2개 이상이면(실측 **30.7%**, 최대 14개) 맨 위·가장 큰 하나만 남기고
나머지를 Section-header 로 강등한다. ② AI-Hub 의 진짜 줄 텍스트를 보고, 영역 안 줄의
60% 이상이 목록 기호(`-·○①1)가.`)로 시작하면 List-item 으로 바꾼다.

육안 검수(표본 6쪽)에서 **Table 박스는 실제 표에 잘 맞았고**, 페이지의 75% 이상을 덮는
과검출은 5.4% 뿐이다(Table 면적비 중앙값 0.13). Table 이 영문 gold 의 6배인 것은 오류가
아니라 **한국 공공문서가 표 중심**이라는 반영이다(KDoc 테스트의 86% 가 표).

⚠ 한계 — List-item 1.6% 는 영문 13.3% 에 못 미친다(규칙이 보수적이고, 신고서·서식에는
불릿 목록이 실제로 적다). 그리고 의사 라벨은 **교사 모델의 오류를 정답으로 굳힌다** —
클래스 정확도는 육안 표본 외에 측정된 바 없다. 물량을 영문 fine gold 대비 과하게 잡지
않는다(**6만 쪽 선**).

보완재가 하나 더 생겼다 — NVIDIA 합성 한국어(§1.7)는 어절/줄/단락 박스와 읽기순서가
**생성기 GT** 다(교사 모델 추정이 아니다). 다만 클래스가 fine 규약(Title·Table…)이 아니라
3단 계층뿐이고 합성 문서라, 의사 라벨을 대체하지는 못한다. 둘은 서로 다른 구멍을 메운다 —
의사 라벨은 진짜 한국 공문서의 **클래스**, NVIDIA 는 대량의 정확한 **박스·읽기순서**.

### 3.8 페이지 silver 를 만들며 드러난 결함 3건 (2026-08-12)

silver(§1.8)를 만들려고 기존 산출물을 처음으로 **페이지 단위로** 교차 검증했더니 셋이 나왔다.
셋 다 crop 단위로만 보면 안 보이는 것들이다.

**① 71299 줄 GT 에 완전 중복 레코드 18.6%.**
`aihub_ocr/71299/crops_lines_train.jsonl` 5,764,232줄 중 **1,313,829줄이 (bbox, 텍스트)가
완전히 같은 중복**이다. 다른 3개 데이터셋(632·71300·71301)은 0건이라 71299 빌드만의 문제다.
→ **§1.2 의 "71299 인식(crop) 7,078,061" 은 중복 포함 수치다.** 고유는 5,764,232 이며,
학습에서 그 줄들은 두 번씩 학습되고 있다(한국어 crop 물량이 실제보다 18.6% 부풀어 있다).

라벨 항목 자체에 없다. 구조를 가진 71709 는 원천이 전부 (표 crop, 표 HTML) 쌍이고 **원본 페이지
이미지도, 페이지 안 좌표도 없다**. 그래서 "페이지 + 그 페이지 표의 구조" 를 함께 가진 AI-Hub
데이터셋은 존재하지 않는다. 한쪽은 페이지가 있고 구조가 없으며, 다른 쪽은 구조가 있고 페이지가
없다 — §1.9 가 그 빈칸을 메우는 방식이다.

**③ 632 줄 GT 좌표가 이미지와 어긋난다.** 표본 400쪽 중 **128쪽(32%)** 에서 줄 GT 의
y 최대값이 이미지 높이를 **1.05~1.15배** 초과한다(x 는 0.67 로 여유). 라벨이 다른 배율·크롭
기준으로 만들어졌다는 뜻이다. 페이지 조립에는 못 쓰고(그래서 632 는 2쪽만 통과), crop 학습에는
영향이 없다(crop 은 bbox 로 자른 이미지를 쓰므로 페이지 좌표계가 필요 없다).
→ 632 를 페이지 계열에 넣으려면 **배율 보정이 먼저**다.
