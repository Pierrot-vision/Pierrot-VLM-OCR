## 2. 표 26.9% — 절반 이상이 "읽기 실패"가 아니라 "출력 규약 불일치"

2,460개 표 테스트를 실패 원인별로 분해했다. 채점 규칙을 한 겹씩 완화하며 재채점한 결과다.

| 조건 | 통과율 | 증분 |
|---|---:|---:|
| 현재(공식 규칙) | **26.9%** | — |
| 첫 행·첫 열을 `<th>` 로 표시 | 33.9% | **+7.0pt** |
| ↑ + 셀 공백/줄바꿈 무시 | 43.6% | **+9.7pt** |
| ↑ + 오타 2자 허용 | 48.1% | +4.5pt |

앞의 두 줄(**합 +16.7pt**)은 모델 능력이 아니라 **우리 출력 형식의 결함**이다.

### ① 표 출력에 "헤더" 개념이 아예 없다 (+7.0pt)

관계 테스트 실패 1,329건 중 **left_heading 506 + top_heading 361 = 65%** 가 헤딩이다.

[otsl_to_html()](../../tools/otsl.py#L199-L215) 은 `<td>` 만 낸다 — `<th>` 도 `<thead>` 도 없다.
채점기는 헤더가 하나도 없으면 "왼쪽/위쪽 끝까지 걸어간 셀"을 헤딩으로 대체하므로
엉뚱한 셀을 집는다.

```
독거노인등록통계 108 — GT 고유셀 커버율 99.5%(내용은 거의 완벽)인데 표 통과 22.9%
  cell='4,502' 기대 left_heading='계'  → 실제 '80~84세'   (179개 중 137개가 이 실패)
  cell='1,271' 기대 top_heading='계'   → 실제 '주요 5대 노인질병'
```

근본은 [OTSL 문법](../../tools/otsl.py#L8-L16) 자체에 헤더 셀 토큰이 없다는 점이다.
학습 GT 에 없으니 모델이 배울 수가 없다. **PubTabNet 원천 HTML 은 100% `<thead>` 를 갖고
있는데 우리가 변환 과정에서 버리고 있었다.**

### ② 셀 안 줄바꿈이 공백 없이 붙는다 (+9.7pt)

[html_to_otsl 의 셀 텍스트 수집](../../tools/otsl.py#L73-L75)이 `<br/>` 을 텍스트 없는 태그로
흘려버려 줄이 그냥 이어붙는다. 벤치마크 GT 는 줄바꿈을 공백으로 잇는다.
표 테스트는 `max_diffs: 0`, 즉 **완전일치**라 공백 하나가 곧 실패다.

```
기대 '데이터 제공량(GB)'                 → 우리 '데이터제공량 (GB)'
기대 '태풍 빈발 시기 우리나라에 영향을…'   → 우리 '태풍 빈발 시기우리나라에영향을…'
```

학습 GT 도 같은 병을 앓는다(aihub_tables 실제 레코드):
`<fcel>교육내용및 교과목특이사항`, `<fcel>소속및 직위`.
12자 이상인데 공백이 하나도 없는 셀이 **6.8%** 다.

### ③ 파국 페이지 — 표 테스트의 9.6%가 자동 0점

| 페이지 | 표 테스트 | GT셀 커버율 | 원인 |
|---|---:|---:|---|
| 부산 기장군_통계연보2 31 | 70 | **0.0%** | 레이아웃이 Table 을 못 잡음 |
| 대전 도시공원 및 녹지현황 19 | 144 | **0.7%** | `<lcel>` **324개 연속** 퇴행 → `<td colspan="682">` 하나 |
| 한국토지주택공사_열요금 71 | 162 | 5.1% | "1999년 12월 31일" 수백 회 반복(41KB 출력) |
| 가스안전공사 2 | 74 | 7.2% | Table 미검출 |

[run_pages.py 의 `--stop-on-cycle`](../../benchmark/run_pages.py#L54-L58) 기본값이 **0(비활성)** 이다.
greedy 디코딩 + 반복 억제 없음이라, 조밀한 표에서 한 번 미끄러지면 페이지 전체가 죽는다.

### ④ 표본 편향 주의

표 테스트 2,460개 중 **상위 7쪽이 1,162개(47%)** 다. "표 점수"는 사실상 통계연보급 대형 표
몇 장의 성패다. 51쪽(7%) 표본이라 분산이 크다 — 정식 수치는 전량 채점이 필요하다.

## 3. 텍스트 60.3% — 25%는 오독, 15%는 아예 없음

| 채점 완화 | 통과율 |
|---|---:|
| 공식 | 60.3% |
| 공백 무시 | 67.1% |
| 유사도 90% 이상 | 76.8% |
| 유사도 70% 이상 | **85.0%** |

→ 약 **25%는 "대충 읽었지만 글자가 틀림"**, 약 **15%는 출력에 존재조차 안 함**이다.

**레이아웃 패스가 본문을 흘린다.** 페이지 통읽기 모드가 c2f 보다 텍스트 점수가 *높다*
(66.3% vs 60.3%, [codex_eval_stage3_pagemode.json](../../results/codex_eval_stage3_pagemode.json)).
검출→crop 경로에서 내용이 새고 있다는 뜻이다.

**환각** — 못 읽으면 지어낸다.

```
- 카드드드프로젝트는 2015년 3월 20일에 출시되었습니다.   ← 문서에 없는 문장
- · 내천,시,구,특선은 인정하여,영부이 없는,문서,내적
```

작은 글자를 못 읽을 때 0.6B 디코더가 언어모델 prior 로 그럴듯한 한국어를 만들어낸다.
NED 평균으로는 안 보이고 present 테스트에서만 드러난다.

## 4. 진짜 근본 원인 — 한국어 **레이아웃** 실데이터가 없다

Stage 1B/2 배합([run_stage_pipeline.sh](../../scripts/run_stage_pipeline.sh#L254-L255))에서
`fine` 규약 레이아웃 소스는 전부 이것뿐이다.

- ccpdf (영문 PDF) ×4~×8 오버샘플
- DocLayNet (영문)
- DocSynth300K (합성 영문)
- **synth_ko 19,700건 — 유일한 한국어, 그나마 합성**

AI-Hub 한국어 검출 24만 건은 있지만 **`wild`(어절 박스) 규약**이라 문서 레이아웃과
출력 규약이 다르다. 결국 `Layout Detection (fine):` 를 한국 공공문서에 걸면 **완전한 OOD** 다.
인식(crop)은 한국어가 49% 인데 **검출만 비어 있는 비대칭**이 c2f 파이프라인의 1단계를 무너뜨린다.

## 5. 해상도는 이 벤치의 병목이 아니다

2MP → 4MP 실험에서 **51개 중 49개가 바이트 단위 동일**, 모든 집계 점수 무변화.
검출된 표 crop 65개 중 2MP 를 넘는 건 2개뿐이었다([KDOC_51_REPORT.md](../../codex_eval/KDOC_51_REPORT.md)).
plan.md 가 1순위로 둔 "① 인식 해상도 상향"은 최소한 KDoc 에서는 근거가 없다 —
조밀한 표일수록 crop 자체는 작기 때문이다.

## 7. 적용 내역 (2026-08-11, 학습 없이 가능한 것 전부)

### ✅ 1·2 — 표 정답 규약 수정 + 기존 GT 갱신

- [tools/otsl.py](../../tools/otsl.py): 헤더 셀 토큰 **`<ched>`** 추가(`<th>`/`<thead>` ↔ `<ched>`),
  셀 안 `<br>/<p>/<div>/<li>` → **공백 한 칸**. 왕복 검증·구버전 OTSL 하위호환 확인.
  토큰 비용도 그대로다(`<ched>` 3토큰 = `<fcel>` 3토큰).
- [tools/refresh_table_otsl.py](../../tools/refresh_table_otsl.py) 신규 — 이미지 재추출 없이
  **정답만** 다시 만든다.

| 대상 | 결과 |
|---|---|
| PubTabNet train | 199,500건 전부 재생성, **99.8%가 `<ched>` 보유**, 유실 0 |
| PubTabNet val | 500건 100% |
| synth_ko_v2 표 | 16샤드 **58,993건** 100% (구조 규칙, 재렌더 불필요) |
| **AI-Hub 71709** | **104,437 / 104,758 (99.7%)** — §8 에서 구조 규칙으로 복원 |
| **FinTabNet** | **59,589 / 61,301 (97.2%)** — 원천 parquet 도 `<th>` 0% 라 §8 규칙 적용 |
| sparsetables | **의도적 제외** — 셀이 `BCF`·`UWN` 무작위 3글자라 머리글 개념이 없다 |

- [tools/synth_korean_docs.py](../../tools/synth_korean_docs.py): 앞으로 만드는 한국어 합성 표는
  머리글을 `<ched>` 로 낸다(음영 칸이 곧 머리글이라 GT 가 정확하다).
  (§8.3 에서 AI-Hub 71709 에도 구조 규칙으로 헤더를 넣어, 한국어 헤더 데이터는 이제 16.4만이다.)

### ✅ 3 — 디코딩 가드 + 표 토큰 상한

**⚠ 정정: 반복 차단은 점수를 올리지 않는다.** 9쪽 ablation 을 직접 채점한 결과다.

| 조건 | 출력 크기 | micro |
|---|---:|---:|
| 가드 OFF | 83,139자 | 7.3% |
| 가드 ON (주기 ≤8) | 57,924자 | 7.3% |
| 가드 ON (주기 ≤32) | **40,252자** | **7.3%** |

반복이 시작된 뒤의 토큰은 어차피 전부 오답이라, 이건 **점수 장치가 아니라 위생 장치**다
(출력 절반·생성 시간 단축). 그래도 기본 ON(32)으로 바꿨다 — 잃을 게 없다.

**반면 토큰 상한은 실제 손실이었다.** 예측 표 65개의 토큰 수를 재보니 **8개(12%)가
2046~2130 에 군집** — 정확히 2048 상한에서 잘린 흔적이다. 통계연보급 표는 아래쪽 행이
통째로 사라진다. → [run_pages.py](../../benchmark/run_pages.py#L47-L52) ·
[infer_pierrotocrvlm.py](../../infer/infer_pierrotocrvlm.py) 에 `--table-max-new-tokens`(기본 4096)
를 넣고, 추론 스크립트에도 없던 반복 가드를 연결했다.

### ◐ 4 — 한국어 레이아웃: 실데이터는 불가, 합성 3배 투입

AI-Hub 검출 라벨에는 **클래스가 없다**(전부 `Text`, 어절/줄 단위 = `wild` 규약).
fine 규약(Title/Section-header/Table/Picture…)을 만들 수 없어 **실문서 재라벨은 보류**한다 —
헤아려 만든 클래스는 GT 가 아니라 추측이고, pseudo-label 은 GPU 가 비어야 한다.

대신 이미 빌드돼 있으나 **파이프라인에 연결되지 않았던 `synth_ko_v2` 를 투입**했다.

| | synth_ko (v1) | **synth_ko_v2** |
|---|---:|---:|
| fine 레이아웃 | 19,700쪽 | **59,699쪽 (3배)** |
| 한국어 표 | 25,950 (셀이 무작위 단어) | **58,993 (공공 통계표 모사 + 헤더)** |
| crop / 페이지 | 117,438 / 19,700 | 352,699 / 59,699 |

[run_stage_pipeline.sh](../../scripts/run_stage_pipeline.sh#L40-L50) 가 v2 가 있으면 자동으로 쓴다
(없으면 v1 폴백). Stage 1B 레이아웃 19,700→40,000, Stage 2 19,700→50,000 으로 올렸다.

### ✅ 5 — 외부 벤치를 학습 루프에 편입

[eval/bench_generalization.sh](../../eval/bench_generalization.sh) 신규 —
체크포인트 하나를 KDoc 51쪽으로 채점한다(GPU 6장, ~4분).
[run_stage_pipeline.sh](../../scripts/run_stage_pipeline.sh) 의 `run_stage` 가 단계마다 자동 호출한다.
실패해도 학습은 계속한다(채점은 관측이지 게이트가 아니다). `PIPELINE_BENCH=0` 으로 끌 수 있다.

### ⏸ 6 — Stage 2 vs Stage 3 비교는 GPU 대기

ODB 는 이미 stage3 열세를 보이지만(text NED 0.260 → 0.365) KDoc 은 stage3 만 쟀다.
지금 GPU 8장이 전량 채점 중이라 끝나면 아래를 돌린다.

```bash
eval/bench_generalization.sh outputs/pierrotocrvlm_stage2/final stage2
```

### 재학습이 있어야 효과가 나는 것

`<ched>` 는 **모델이 아직 낼 수 없다** — 규약과 데이터만 준비됐다.
표 단계(1B/2)를 다시 돌려야 실측 +16.7pt 가 실현된다.

## 8. 벤치와 학습셋의 분포 대조 (2026-08-11)

§4 는 "한국어 **레이아웃** 실데이터가 없다"를 근본으로 짚었다. 벤치 원본을 직접 뜯어
학습셋과 대조하니, 더 넓은 **층위 어긋남**이 보인다.

### 8.1 KDoc 이 실제로 묻는 것

849개 PDF 전부 한국 공공문서다(통계 283·보고서 238·매뉴얼 216·공고 112).
테스트 56,197개 중 **표가 49,115개(87%)** — 셀의 상하좌우·머리글을 맞히는 구조 테스트다.

| | |
|---|---|
| `left_heading` 요구 | **78%** (38,520건) |
| `top_heading` 요구 | 59% (28,763건) |
| 셀이 숫자·기호뿐 | **63%** (통계표) |
| 표당 서로 다른 `left_heading` | 중앙값 **8종** (계층 헤더) |
| 머리글 생김새 | `구분 Division`, `총계 Total` — 국한혼용 + 영문 병기 |

### 8.2 어긋남 — 도메인은 있는데 층위가 없다

| 층위 | 한국 공공문서 실데이터 |
|---|---|
| crop 텍스트 인식 | **있음** — 71299 공공문서 708만, 88 행정서식 330만 |

**한국 공공문서를 crop 단위로는 수백만 건 봤지만 한 페이지 통째로는 한 번도 안 봤다.**

점수가 높다(66.3% vs 60.3%)"가 정확히 그 증상이다.

### 8.3 ✅ AI-Hub 표 10.4만 건에 헤더 복원 — §7 의 "손대지 않음" 정정

§7 은 AI-Hub 를 "원천에 헤더 정보가 0% 라 손대지 않음"으로 넘겼다. 원천 HTML 3,000개를
직접 열어 `<th>`·`<thead>`·style 속성이 **전부 0%** 임은 확인했다. 그런데 §2 가 실측한
**+7.0pt** 자체가 원천 주석이 아니라 *"첫 행·첫 열을 `<th>` 로 표시"* 하는 **구조 규칙**
에서 나온 값이다. 같은 규칙을 학습 GT 에 걸면 된다.

규칙이 정당한지 **벤치 정답으로 직접 쟀다**.

| 검증 | 결과 |
|---|---|
| `left_heading` 이 본문 첫 열 셀과 일치 | **73.6%** (38,520건 중) |
| `top_heading` 이 테스트된 셀과 일치 | 7.5% → 머리글이 본문 위 **별도 밴드**에 있다는 뜻 |
| 71709 첫 행이 전부 비숫자 라벨 | **96.6%** (표본 2,000) |
| 71709 첫 열이 전부 비숫자 라벨 | **89.4%** |

> ⚠ 처음에 "첫 행 규칙 적중률 1.7%"로 쟀다가 정정했다. **열 머리글은 애초에 테스트 대상
> 셀이 아니라서** 그 방법으로는 잴 수 없다. 두 수치를 합치면 오히려 규칙을 뒷받침한다 —
> 행 머리글은 본문 첫 열에, 열 머리글은 본문 위 별도 밴드에 있다.

[refresh_table_otsl.py](../../tools/refresh_table_otsl.py) 에 `heuristic` 모드를 넣었다.
**틀린 GT 를 만들지 않도록 행·열을 따로 판정**한다 — 숫자가 하나라도 섞인 행/열은 손대지
않는다. 1행이 `<lcel>` 로 가로병합되고 아래 행에 숫자가 없으면 **2단 헤더**로 본다.

| | |
|---|---|
| 변경 | **104,437 / 104,758 (99.7%)** |
| 첫 행+첫 열 / 첫 행만 / 첫 열만 | 90,891 / 9,112 / 4,434 |
| 2단 헤더 검출 | **31,441** |
| 건너뜀(1행·0열 모두 숫자) | 321 |
| 왕복 검증(otsl→html→otsl) | 300/300 |

**한글 표 + 헤더: 58,993 → 163,751건(2.8배), 그중 10.4만이 실문서다.**
헤더 보유 표 전체는 PubTabNet 199,500 + AI-Hub 104,758 + synth_ko_v2 58,993 = **36.3만**.

### 8.4 ⚠ 지금 도는 학습은 이 수정을 하나도 못 받는다

[run_stage_pipeline.sh](../../scripts/run_stage_pipeline.sh) 는 실행 중 원본 수정에 대비해

지켜준 대신, **나중에 넣은 수정도 함께 막는다.**

| 시각 | 사건 |
|---|---|
| 08-08 13:30 | 스냅샷 생성 — 이 시점 코드로 고정 |
| 08-10 03:06 / 16:35 | Stage 1B / Stage 2 배합 생성 (옛 GT) |
| 08-11 21:08~ | `<ched>`·PubTabNet 재생성·synth_ko_v2·벤치 편입·AI-Hub 헤더 |

스냅샷에 `synth_ko_v2`·`PIPELINE_BENCH` 문자열이 **0건**이다.
→ **표 단계(1B/2) 재실행 없이는 §7·§8 의 실측 +16.7pt 가 실현되지 않는다.**

### 8.5 FinTabNet 도 같은 규칙으로 — sparsetables 는 제외

FinTabNet 원천(`fintabnet-html/en/*.parquet`, 컬럼 `html_table`)을 열어 보니 여기도
`<th>`·`<thead>` 가 **0%** 였다. parquet 모드로는 복구가 안 되고, 같은 구조 규칙을 걸었다 —
**59,589 / 61,301 (97.2%)**, 2단 헤더 8,883, 건너뜀 1,712.

**sparsetables 36,671 은 일부러 뺐다.** 첫 행이 `BCF`·`UWN`·`LTP` 같은 **무작위 3글자**다.
머리글 개념이 없는 합성 표에 규칙을 걸면 GT 를 지어내는 것이다(§7 synth_ko 구버전과 같은 함정).

**표 GT 헤더 일관성 92%** (422,074 / 461,223). GT 가 섞이면 모델이 "언제 `<ched>` 를
내야 하는지"를 못 배우므로, 남은 8% 는 sparsetables 뿐이라는 게 중요하다.

★ **이 결과가 증명하는 범위를 넘겨 읽으면 안 된다.** OOD val 은 **같은 합성 렌더링

→ 그래서 결론은 "잘 배웠으니 더 넣자" 가 아니라 **topology 합성 물량 추가 중단** 이다.

### 10.3 ★ 그런데 목표가 틀렸다

KDoc **예측** 표의 좌측 깊이 ≥2 비율: **V3 0.9% · V3.3 0.9%** (좌측 rowspan 48.2/48.3%).

★ **이건 예측 출현율이지 GT 출현율이 아니다.** tables.jsonl 에는 셀 관계 질의만 있고
  표 구조 GT 가 없다. "두 모델이 0.9% 만 냈다 → 이미지에도 0.9% 뿐이다" 는 성립하지
  않는다 — 둘 다 실스캔의 2단 구조를 못 잡았을 가능성이 남는다. 정확히는:

| 확정 | 합성 도메인에서 unseen 어휘 2단 구조 복원 **100%** |
|---|---|
| 확정 | KDoc left_heading **+1.0p** 만 개선(조건부로는 +1.4p) |
| 확정 | 합성 topology 증량이 KDoc 총점을 못 올림 |
| **미확정** | **KDoc 실표의 2단 좌측계층 GT 출현율** |

  미확정의 가능한 원인: ① 실제 출현율이 낮다 ② 실스캔에서 구조 검출 실패
  ③ crop·해상도로 좌측 계층 열이 잘림 ④ OTSL 변환에서 계층이 평탄화.

전제가 (적어도 부분적으로) 틀렸다. 최초 근거였던 *"KDoc 이 요구하는 것이 left_heading 78%"* 는
**left_heading 이 테스트되는 비율**이지 **표가 2단 계층을 갖는 비율**이 아니다.
KDoc 좌측 헤더 상위는 `계·합계·2020·제주` 로 전부 **1단 행머리글**이고 V3 는 이미
53.7% 맞히고 있었다. 엄격 긴표×좌측계층을 0.017% → 9.96%(550배) 넣어 얻은 것은 left_heading **+1.0p** 다.
다만 "그게 가용 여지의 전부였다" 고 단정할 수는 없다 — GT 출현율이 미확정이기 때문이다.

**교훈: 벤치의 "테스트 비율" 을 "구조 출현율" 로 오독하면 사이클 하나를 통째로 버린다.**

### 10.4 표 내부는 오히려 좋아졌는데 상쇄됐다

| | V3 | V3.3 | |

★ 위 네 값은 **주변 비율**이다. `셀값 68.0% × 위치 72.0% = 48.7%` 처럼 곱하면 안 된다 —

### 10.5 머리말 −2.40p — 원인 특정

### 10.6 V3.4 방침

- **표 topology 확대 중단.** OOD 100% 로 포화됐고 목표 자체가 ~1% 였다.
- **머리말 형태 교정** — 쪽번호를 머리말에 합치고 `【별첨】` 류 추가. 원인이 특정됐고 값싸다.
- **셀 인식 실패 11.2% · 위치 70.2% · top_heading 62.9%** 가 남은 큰 항목이다.
- 게이트는 유지하되 **"게이트 통과 = 성능 향상" 이 아님**을 기록한다. V3.3 은 12개를
  전부 통과하고도 V3 에 졌다. 게이트는 **과거 실수 재발 방지**이지 성능 보증이 아니다.

### 12.2 cycle 재활성 — 점수로는 기각, 비용 레버로만

| 설정 | 최대주기/반복 | 상한 도달 | 생성 토큰 중앙 | 표 점수 |
|---|---|---|---|---|
| base | 비활성 | **33.5%** | 1,380 | **9.67%** |
| c8r16 | 8/16 | 5.4% | 895 | 9.51% |
| c8r24 | 8/24 | 6.4% | 910 | 9.66% |

폭주는 확실히 잡힌다(상한 도달 33.5 → 3.4%, 토큰 −36%). **그런데 점수는 −0.01~−0.16p.**
그리고 **격자 붕괴는 17.1% → 17.1% 로 그대로다.**

### 12.3 ★ 인과가 뒤집혔다 — 붕괴가 폭주의 원인이다

    (가설)  병합 증가 → 폭주 → 격자 붕괴 → 위치 실패
    (실측)  폭주를 90% 없애도 붕괴율·점수 무변화 → **붕괴가 먼저다**

849쪽 표 crop 1,290개를 정상/붕괴로 갈라 보면:

| | 정상 1,204 | **붕괴 86 (6.7%)** |
|---|---|---|
| 첫 행 셀 수 | 6 | **1,362** |
| 행 수 | 12 | **1** |
| crop 높이 | 779 | **1,421** |
| 종횡비(w/h) | 1.54 | **0.74** |
| 상한 도달 | 8% | **92%** |

**붕괴 86건 중 85건이 `<nl>` 을 한 번도 내지 않는다.** 도중 붕괴는 1건뿐 —
"읽다가 무너지는" 게 아니라 **처음부터 행 구분을 못 한다.**

### 12.4 원인 — 세로로 큰 표가 학습에 없다

| | 학습 표 crop | KDoc 정상 | KDoc 붕괴 |
|---|---|---|---|
| 높이 중앙 | **476** | 779 | **1,421** |
| 높이 1,400+ | **6.1%** | — | — |

학습 표는 중앙 476px 인데 붕괴 표는 1,421px — **3배다.** 그 크기는 학습의 6.1% 뿐이다.
**`--max-suffix-tokens 2900` 필터가 큰 표를 걸러내면서 세로로 큰 표를 학습에서 계속
제거해 왔다.** 추론 예산을 6,144 로 늘려도 안 올랐던 이유가 이것이다 —
**출력 공간이 아니라 학습 분포의 문제였다.**

### 12.5 ★ 정정 — 12.4 의 인과는 틀렸다 (같은 날 재검증)

붕괴한 86개 crop 을 **같은 설정으로 다시 추론**하니 **55개(64%)가 정상**으로 나왔다.
그리디 디코딩인데 결과가 다르다 — 유일한 차이는 **배치 구성**(원본 8개 묶음 → 재추론
2개)이다. 전폭 crop 은 오히려 더 나빴다(정상화 43%).

| 12.4 에서 쓴 것 | 재검증 |
|---|---|
| "세로로 큰 표에서 `<nl>` 실패 = 학습 분포 문제" | **재현율 36%. 입력 속성이 아니다** |
| "학습 476px vs 붕괴 1,421px" | 통계는 사실이나 **인과 근거가 아니다** |
| 처방 "세로로 큰 표 확보" | **근거 없음 — 철회** |

즉 붕괴는 결정론적 실패가 아니라 **배치 의존적 불안정성**일 가능성이 크다. 다만 이번
재추론도 배치 크기·동반 항목을 통제하지 못했으므로 "배치가 원인" 도 아직 확정이 아니다.
확정하려면 배치 1 / 배치 8 / 동일 배치 2회를 나눠 재현해야 한다.

★ 교훈: **재추론 실험은 원본과 배치 구성까지 맞춰야 한다.** 안 맞추면 모델 특성이
  아니라 실험 조건 차이를 측정하게 된다(이 세션 일곱 번째 계측 결함).

### 12.6 처방 (12.5 반영)

- **먼저 붕괴의 재현 조건을 확정한다**(배치 1 / 8 / 동일 배치 2회). 배치가 원인이면
  재학습 없이 추론 설정으로 해결 가능하다.
- 그 전까지 표 데이터 방향(크기·구조·길이)은 **전부 미확정**으로 둔다. 근거 없이
  또 합성 데이터를 만들지 않는다.
- 확정된 별개 사실: 학습·추론 길이 불일치(2,900 / 4,096), 헤더 GT 가 휴리스틱
  (원천 `<th>` 0/300) — 이 둘은 붕괴와 무관하게 남아 있는 문제다.

Long Text 배합 1차 권고에서 `>160자` 구간(통과율 29.6%, 최악)을 주력으로 잡고 합성 긴 페이지

### 15.1 무엇이 문제였나 — 임계값이 아니라 "안 낸 것"

레이아웃 패스가 우단 상단(y131~488)을 **아예 생성하지 않았다.** 걸러낸 게 아니다.

★ **모델은 그 글을 못 읽는 게 아니라 읽기순서에서 건너뛴다.** 토큰 확률로도 확인했다 —

캐시 구현은 옳고, 0.4 대 0.22 같은 얇은 결정이 반올림 잡음에 뒤집힌다는 뜻이다
